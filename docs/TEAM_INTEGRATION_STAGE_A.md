## A. Forensics responsibilities

**Will eventually do [PROPOSED/NOT IMPLEMENTED]:**
- Receive incidents and containment proposals.
- Investigate synthetic security evidence with read-only forensic tools
  (log search, host/user context, MITRE lookup, IP enrichment, timeline).
- Publish findings with cited evidence and confidence.
- Take, defend, challenge, and revise debate positions on containment
  proposals (explicit revision audit trail).
- Send recommendations and votes; submit a final incident report.

**Explicitly OUT of scope:**
- Executing containment/recovery actions (that belongs to those agents).
- Writing to any real system: all forensic tools are read-only over
  synthetic scenario data except `submit_incident_report` (report artifact).
- Policy/legal adjudication (Compliance agent's domain).

## B. Architecture [VERIFIED/IMPLEMENTED (foundation)]

Four layers, behind frozen contracts:

- `contracts/` — Pydantic v1 schemas (strict, UTC, confidence 0..1,
  JSON-Schema exportable). All boundary data is one of these types.
- `forensics.inference` — abstract `InferenceBackend`
  (generate / generate_structured / health_check / get_model_metadata) with a
  working mock. Stage B adds a Transformers backend (SOC fine-tune) and a
  llama.cpp OpenAI-compatible backend (the Foundation-Sec-8B server already
  running at `http://127.0.0.1:8000/v1` — we will only call it, never
  restart or reconfigure it).
- `forensics.tools` — abstract `ForensicTool` + registry for the seven
  tools; every invocation returns an audit record (`ToolInvocation`).
  Working mocks ship with the foundation.
- `forensics.messaging` (AGNTCY runtime transport) and `forensics.reasoning`
  (investigation/debate logic) are Stage B — only their typed contracts and
  directory ownership exist today.

Separately, `coordination/` is an INTERNAL dev-time message bus for our six
coding agents — not part of the council runtime and irrelevant to your
integration (documented in docs/CODING_AGENT_COMMUNICATION.md).

## C. Shared contracts [VERIFIED/IMPLEMENTED as schemas; REQUIRES TEAM AGREEMENT as shared format]

All schemas live in `contracts/` (Pydantic v2, `extra=forbid`, UTC
timestamps, enums, confidence 0..1) and are exported to
`docs/schema_export.json`. Summary:

| Model | Key fields |
|---|---|
| Incident | incident_id, scenario_id, created_at, severity(CRITICAL..INFO), affected_hosts[], initial_description, current_status(OPEN..CLOSED) |
| Evidence | evidence_id, incident_id, source, event_type, timestamp, host_id, description, raw_data{}, collected_at, collection_tool |
| CouncilMessage | message_id, incident_id, round>=0, sender, recipients[], message_type(9 values), timestamp, payload{}, correlation_id |
| InvestigationRequest | request_id, incident_id, round, question, available_evidence_ids[], requested_by |
| InvestigationFindings | agent_id, incident_id, round, findings, cited_evidence_ids[], confidence, uncertainties[], timeline[], recommended_actions[] |
| DebatePosition | agent_id, incident_id, round, position(SUPPORT/OPPOSE/ABSTAIN), supporting/opposing_evidence_ids[], reasoning, confidence, conditions_to_change_position[] |
| PositionRevision | previous_position, new_position, triggering_evidence_ids[], explanation |
| ToolInvocation | invocation_id, incident_id, tool_name, arguments{}, result{}, referenced_evidence_ids[], error?, duration_ms>=0 |

Council message types: INCIDENT_ALERT, EVIDENCE_REQUEST, EVIDENCE_RESPONSE,
FINDING, PROPOSAL, CHALLENGE, REVISION, VOTE, ESCALATION.

A full example (Incident + evidence + one message of each kind) is in
section I.

## E. Message exchange (runtime council)

**[REQUIRES TEAM AGREEMENT]** Envelope: `CouncilMessage` with correlation IDs.

What forensics EXPECTS TO RECEIVE (Stage B):
- `INCIDENT_ALERT` — new incident assigned (payload: Incident).
- `EVIDENCE_REQUEST` — council asks forensics to investigate
  (payload: InvestigationRequest).
- `EVIDENCE_RESPONSE` — additional evidence supplied by any agent
  (payload: Evidence).
- `PROPOSAL` — containment proposal to evaluate (payload: team-defined
  proposal object; see section J).
- `CHALLENGE` — someone disputes our findings (we answer or revise).

What forensics PLANS TO SEND:
- `FINDING` — payload InvestigationFindings (with cited_evidence_ids).
- `CHALLENGE` — we dispute unsupported recommendations (payload cites
  evidence and reasoning).
- `REVISION` — payload PositionRevision when new evidence changes our stance.
- `VOTE` — final stance on a proposal.
- `ESCALATION` — confidence too low / evidence insufficient / deadlocked.

Round semantics: every message carries the debate round; revisions link
previous -> new position with triggering evidence and an explanation, so the
debate history is fully auditable.

## F. Evidence structure [REQUIRES TEAM AGREEMENT]

- `evidence_id`: stable, unique, never reused ("EV-<incident>-<seq>" by
  convention). Once published, an ID always means the same evidence.
- Provenance: `source` (which log/system/tool produced it), `collected_at`
  (UTC), optional `collection_tool`.
- `raw_data` is a serializable dict; large blobs should be referenced, not
  embedded (suggest a shared evidence store path per incident).
- Other agents reference evidence ONLY by `evidence_id` in
  `cited_evidence_ids`, `supporting_evidence_ids`, etc. Forensics will
  validate that IDs it is asked about exist in the shared store.

Open question for the simulator owner: who mints evidence IDs, and where do
agents fetch evidence payloads by ID?

## H. Dependencies on teammates [REQUIRES TEAM AGREEMENT]

From **Containment**: proposal payload schema (what exactly we are voting
on); severity/status vocabulary alignment; who sends INCIDENT_ALERT.
From **Recovery**: what recovery-context evidence will exist so we can cite
it (e.g. backup job logs proving a "suspicious transfer" was sanctioned).
From **Compliance**: what regulatory/policy constraints our
recommended_actions must respect; escalation criteria.
From **shared simulator**: the synthetic evidence store + evidence-ID minting
(see F), scenario IDs mapping to our `scenario_id`, and ground truth for
evaluating our findings.
From **shared messaging deployment**: transport decision (G), channel
naming, and a decision on discovery/identity (we suggest deferring DIR for
the 24-hour event).


## I. Integration example (synthetic data)

Scenario "SCN-exfil-001": a large outbound HTTPS transfer from `web-01` to
`203.0.113.50`. Proposed message sequence between the four agents:

1. **Containment -> all: INCIDENT_ALERT** (round 0)
   `{"incident_id": "INC-2026-001", "scenario_id": "SCN-exfil-001",
     "created_at": "2026-10-10T12:00:00+00:00", "severity": "HIGH",
     "affected_hosts": ["web-01"],
     "initial_description": "Suspicious 2.1GB outbound transfer from web-01",
     "current_status": "OPEN"}`

2. **Containment -> Forensics: EVIDENCE_REQUEST** (round 1, correlation CM-1)
   `{"request_id": "REQ-INC-2026-001-1", "incident_id": "INC-2026-001",
     "round": 1, "question": "Was data exfiltrated from web-01, and how?",
     "available_evidence_ids": ["EV-INC-2026-001-0001"],
     "requested_by": "containment-agent"}`

3. **Forensics investigates** (read-only tools over the shared synthetic
   store; every call logged as a ToolInvocation with evidence references).

4. **Forensics -> all: FINDING** (round 1, correlation CM-1 thread)
   `{"agent_id": "forensics-agent", "incident_id": "INC-2026-001", "round": 1,
     "findings": "Confirmed exfiltration to 203.0.113.50 via HTTPS",
     "cited_evidence_ids": ["EV-INC-2026-001-0001"], "confidence": 0.85,
     "uncertainties": ["Destination ownership unconfirmed"],
     "timeline": [{"timestamp": "2026-10-10T12:00:00+00:00",
                   "description": "Transfer began",
                   "evidence_ids": ["EV-INC-2026-001-0001"]}],
     "recommended_actions": ["Block 203.0.113.50 at egress"]}`

5. **Containment -> all: PROPOSAL** (round 2): "Isolate web-01 immediately."

6. **Forensics -> all: FINDING-carrying position / VOTE support** (round 2)
   DebatePosition SUPPORT with reasoning "Isolation preserves evidence and
   stops ongoing exfiltration", confidence 0.8,
   conditions_to_change_position: ["Transfer proven to be a sanctioned backup"].

7. **Recovery -> all: EVIDENCE_RESPONSE** (round 3, new evidence
   `EV-INC-2026-001-0002`: backup job log showing a scheduled 02:00 backup
   of that size to that destination).

8. **Forensics -> all: REVISION** (round 3) — PositionRevision with
   previous_position SUPPORT -> new_position OPPOSE, triggering_evidence_ids
   `["EV-INC-2026-001-0002"]`, explanation "Transfer matches the sanctioned
   backup schedule". **Compliance** votes on policy grounds; the council
   records the debate history end-to-end via correlation IDs.

Every message above validates against the schemas in
`docs/schema_export.json` [VERIFIED/IMPLEMENTED as schemas]. The agent
behavior itself is [PROPOSED/NOT IMPLEMENTED] until Stage B.

## J. Decisions requiring team agreement

1. **Proposal payload schema** — what exactly a containment PROPOSAL
   contains (actions, scope, rollback, urgency).
2. **Transport** — SLIM on ARM64 vs. A2A-over-HTTP (G); who hosts it.
3. **Evidence store & ID minting** — shared location, who assigns
   evidence_ids, how agents fetch by ID (F).
4. **Incident severity/status vocabularies** — adopt ours or merge?
5. **Correlation & round conventions** — our threading rules (correlation_id
   links every reply to the original message; round advances on each council
   cycle) need to be shared by all four agents.
6. **Identity scheme** — configured agent IDs ("forensics-agent",
   "containment-agent", ...) for the demo; defer DIR/Identity?
7. **Escalation criteria** — when confidence/evidence thresholds force
   ESCALATION instead of a vote.
8. **Simulation timing** — rounds per incident, and who drives the debate
   loop (shared orchestrator vs. agents polling on their own).
